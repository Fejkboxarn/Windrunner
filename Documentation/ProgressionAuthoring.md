# Progression authoring and acceptance

This is a framework and engineering fixture, not demo story content. Existing playground wiring/tuning is unchanged. No dagger design, IK or procedural foot placement is included.

## Create content

1. In Unity open **Tools > Windrunner > Progression Studio**. Create a catalog at a new asset path. The Inspector also supports standard Unity editing. Play Mode editing is disabled; services snapshot definitions at startup.
2. Select **relationships**, Add, and enter a display name/localization identifier. Keep the generated stable ID permanently. Add rank display names and chapters. A chapter needs its own stable ID, quest ID, next rank (1, 2, ...), reward IDs and unique cutscene ID. No fixed character or rank count exists.
3. Under **quests**, Add a story quest and copy the character/chapter IDs. Story quests must use explicit turn-in. Set text/localization IDs, prerequisite quest IDs, optional guidance area/clue, and rewards. Do not assign the same reward at both quest and chapter level.
4. Add objective groups. Give each group a stable ID; groups with no prerequisites are parallel. To create a later stage, add earlier group IDs to its requiresGroups list. For individual objective prerequisites, place that objective in its own group. Cycles are rejected.
5. Each objective needs a unique ID within its quest, description, kind, count and matching definition/region filters. Default evaluator `fact` supports enemy, race, collection, discovery, interaction, puzzle and traversal facts. New evaluators register with ProgressionService at composition; ordinary content needs no C#.
6. Set uniqueTargets for unique object collection. Set PersistentRetroactive only when earlier persistent discoveries/items/puzzles should count. Combat and timed attempts default to AfterAcceptance. Stable object identity and occurrence identity serve different purposes: repeated legitimate actions need new occurrences; duplicate callbacks reuse the original occurrence.
7. Under **challenges**, define independent world challenges and first-clear rewards. A challenge has no relationship authority. Assign prerequisites and replay policy. Race/TraversalCompleted and PuzzleCompleted kinds must match objective references.
8. Under **races**, reference the challenge, add ordered checkpoint steps, and list allowed alternative checkpoint IDs per step. The final step is finish. A zero time limit means untimed traversal. Time follows gameplay scaling: pause/hit-stop affect both movement and race clocks. A failed/canceled attempt leaves parent quests active.
9. Under **puzzles**, reference its challenge and mechanism IDs. Configure order, destination, time window, retry, reset-on-exit and permanence. Persistent partial state requires a permanent untimed puzzle. Quest code does not contain puzzle rules.
10. Under **rewards**, use an ID, kind, content ID and amount. `unlock` entitlements can drive ProgressionUnlockView or requiredUnlockId on interactions. Other kinds are durable claims for future idempotent consumers, not invented inventory/dagger behavior.
11. Under **cutscenes**, assign an authored Timeline/Playable and skip policy. One unique cutscene record per rank-up. The supplied engineering Timeline only activates a test marker for one second. It is not final cinematic content.
12. Use **Validate definitions and content**. Errors include location IDs and asset path. Fix structural errors before saving/playing; missing final Timeline content is reported and remains an explicit content gate. **Save validated catalog** persists only that catalog. Standard Unity Undo applies. **Duplicate with new IDs** copies the catalog and remaps internal references; external scene bindings are intentionally not rewritten.

## Compose a scene

1. Add one ProgressionHost, bind the existing ProjectRoot and catalog, and choose stable player ID and a simple save-slot filename. Do not add another ProjectRoot where one already exists. Multiple independent players/save slots are not implemented by the current single-local-player production root.
2. Add ProgressionActor to the player and bind the host and production input host. Add PlayerInteractionController with that actor, the existing player camera and appropriate interaction layers/reach. No per-frame hierarchy search is used.
3. Put ProgressionInteraction on a collider for a character offer/turn-in, switch, item or discovery. Set stable object ID, command, definition ID, range, allowed channel and prerequisites. Accept/TurnIn commands reference quest IDs. The prompt reflects the centralized binding. Failed range/actor/channel/prerequisite checks produce no progress.

   For a permanent pickup/discovery, enable persistent and select the corresponding fact kind. Add ProgressionFactView on a separate observer object, bind the actor, kind, same stable object ID and presentation object. Leave activeWhenRecorded off to hide a collected object, or enable it for revealed discovery presentation. The observer must remain outside the object it hides; state restores on scene load and re-enable.
4. Add RaceHost with catalog/race ID. A StartRace interaction begins an attempt. Each checkpoint trigger has isTrigger enabled and a ProgressionTrigger referencing the actor, RaceHost and checkpoint ID. Keep checkpoints separate so an actor leaves one before entering another. Use authored alternatives for branches. No instanced mission scenes are created.
5. Add PuzzleHost with actor/catalog/puzzle ID. PuzzleMechanism interactions reference mechanism IDs; PuzzleDestination interactions reference the final destination. Bind solvedStateChanged to ProgressionWorldStateView.SetOpen for an authored gate/route/moving object. Do not bind player transforms. A ProgressionTrigger enclosing the puzzle can reference puzzleArea to reset on exit.
6. For Air Cast switches, add AirflowProgressionAdapter to the player, bind current motor/caster/Dash/Sling and explicit node-to-interaction mappings. Enable AbilityHit on the interaction; configure a range appropriate for that authored ability target. Actual PulseHit callbacks drive it, not Cast button counts. EnemyProgressionAdapter binds an enemy node/health, player actor/Sling and enemy/region IDs; only that player's lethal impact earns a defeat occurrence.
7. Add ProgressionCinematicPlayer with actor/catalog, dedicated PlayableDirector, existing gameplay camera and separate cinematic camera (initially disabled, without a second AudioListener). Bind safety to AirflowProgressionAdapter. The player must be grounded, idle and out of abilities. Timeline may control NPCs/cinematic objects, not the production player hierarchy. Player portable animation remains its pose authority.
8. Add ProgressionJournal with actor/catalog/interaction/cinematic references. Optionally bind general-area ProgressionAreaMarkers; radius is an approximate area, not a route or solution. Journal state derives entirely from the service. Other active quests continue to observe facts regardless of tracking.
9. **Tools > Windrunner > Validate Progression** audits catalogs. Scene host structural validation also runs before Play. Inspect new scene/prefab wiring and Collider trigger configuration explicitly; arbitrary UnityEvent targets remain designer responsibility.

   The scene guard checks interaction identities/ranges/channels, quest/challenge/mechanism references, race/puzzle catalogs, checkpoint trigger IDs and cinematic control bindings. Timeline direct player bindings are rejected at playback. Nested Control/Signal tracks and arbitrary UnityEvent targets still require authoring review; do not use them to disable gameplay components or introduce another player pose writer.

## Practical manual acceptance — initially not tested

1. Open `Assets/WindrunnerProduction/Progression/Fixtures/ProgressionFixture.unity` **alone**. The fixture is excluded from shipping build settings. Play uses its own `progression-engineering-fixture.json`, never the ordinary gameplay slot. For a fresh run, change the fixture host's saveSlot in a copied scene; do not delete real saves.
2. Move with existing movement bindings and aim at the two nearby offer cubes. Press the displayed Interact binding (default E). Both chapters should become active independently. Failure: one acceptance blocks the other or an out-of-range interaction succeeds.
3. Press J to open the journal. Down Arrow selects a quest; T tracks it; J closes. Bindings are rebindable under the existing pause menu's Progression entries. Gameplay/time should pause while the journal is open and resume afterward. Open the pause menu over the journal, resume it, then close the journal. Failure: movement resumes behind either overlay or remains blocked afterward. No mouse cursor takeover is required by this keyboard-first journal.
4. Use the World switch cube. Both accepted quests should credit it once. Chapter B becomes ready, A still needs the race. Retry the same unique interaction where configured: duplicate callbacks must not add credit. Failure: unaccepted nonretroactive quests gain progress.
5. Use Start race, traverse the checkpoint plane near z=12 and finish near z=20 within 30 gameplay seconds. The A objective should become ready. Replaying may improve personal best but grants the first-clear entitlement once and never advances rank. Failure: finishing out of order succeeds, timeout completes a quest, or rewards duplicate. These planes are engineering triggers; inspect them in Scene view to see their bounds.
6. Use Turn in A/B near z=24. Each authorized turn-in should complete its own chapter/rank once and unlock its cinematic. Repeated use must grant nothing. Failure: another character's rank changes or cutscene playback grants additional rewards.
7. Stop on the floor, open J, press C to view the pending engineering cinematic. The marker appears for one second; camera/input return and the record becomes watched. Repeat using Enter to skip, then disable the cinematic component during playback in a copy to test interruption. Failure: wrong camera remains active, gameplay remains frozen, or interruption falsely marks watched. Missing content shows an explicit skip option only when authored skip is allowed; it is never auto-resolved.
8. Use Puzzle switch one then two. Check ordered rejection, successful solution and persistence. Add a gate via solvedStateChanged in a copied fixture to see its state. For reset/time-window testing, duplicate the catalog and set resetOnExit/timeWindow; wire a puzzle-area trigger. Failure: wrong sequence solves, unsolved mechanisms stay active after configured reset, or a temporary puzzle grants retroactive persistent credit.
9. Exit and re-enter Play, or reload the fixture. Completed chapters, entitlements, tracked quest and permanent puzzle state should survive; interrupted cutscenes should be pending and the player playable. Failure: duplicate rewards/services, reset completed ranks, or a save error silently starts a new game.
10. In a copy of the actual gameplay scene, wire an Air Cast target and a lethal Sling enemy through the explicit adapters. Check normal/perfect/canceled Cast and Sling, range, repeated callbacks and enemy respawn. Progress only follows actual hits/defeats. Existing ability timing/resources/camera/animation must feel unchanged. Final authored combat/traversal placement needs this manual acceptance.
11. Review Timeline camera framing, NPC clips, audio, HUD readability, localization lengths, controller bindings and general-area clues with authored content. Automated state/ownership tests do not approve cinematic quality or navigation design.

## Save operations

State is written on meaningful commands, before notifications. There is no separate mandatory Save button. Back up saves before content migrations; never rename stable IDs casually. Unknown retired records remain preserved. Unsupported future schemas/corruption stop progression initialization and log an error; inspect `.bak` deliberately. Do not silently replace a player's save. Changing saveSlot creates a distinct profile, not an implicit reset of the old one.
