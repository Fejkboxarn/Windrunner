# Main menu and playthrough sessions

## Try the player flow

1. Choose **Tools > Windrunner > Open Main Menu**, enter Play Mode and focus the Game view. Use the mouse, arrow keys / Enter, or a controller's stick / D-pad and south button. Backspace or the controller's east button goes back. The normal Pause binding also backs out of nested screens. Continue becomes available when a valid playthrough exists.
2. Choose **New game > Start a new playthrough**. The production character starts at the original playground arrival. Each playthrough has its own GUID, so journeys can share a display name. To replace a journey, select its row, choose **Start over in this slot**, then confirm.
3. Open Pause. **Save game** can update the current playthrough, write an independent copy or explicitly replace another slot. Progression transactions autosave immediately. A sixty-second real-time timer also saves during gameplay. Saving preserves the live character's traversal. Loading always reconstructs the world at the starting clearing with the original spawn orientation and fresh ability, input and camera ownership.
4. Choose **Load game**, select a playthrough, then load it. The list shows local save time and checkpoint; details include completed quest and discovery counts. Continue uses the same validated load path and selects the newest usable record. A slot recovering from backup is labeled. Unusable entries have an explanation. Deleting requires confirmation and the active slot cannot be deleted from its own session.
5. In either menu, open **Settings**. Sound controls master, music and ambience. Display offers resolution, mode, quality, VSync and a frame cap when VSync is off. Apply previews a change for fifteen seconds; cancel or wait to revert. Controls offers independent pointer and stick sensitivity, vertical inversion, binding labels, conflict detection, cancellation and reset. Input and display preferences are independent of saves.
6. Open **Gallery** from the title or a playthrough's detail screen. A previously selected slot takes precedence over the most recent slot. Watched and skipped records unlock their entry. The production catalog currently has no authored cinematics. Future gallery replay uses an explicitly assigned video. It cannot execute quest commands, grant rewards or advance a cutscene record.
7. For manual acceptance, compare the clearing, camera facing, airborne save/reload and restored control with the accepted playground. Listen beside the waterfall, in the forest and near music with each fader at 100% and 50%. Try a physical controller on the long bindings list, cancel an overwrite, and test rollback on the intended display and refresh rate.

## Composition and storage

Branch `feature/main-menu` starts at `9e8f97c4`, the validated progression ancestor of `feature/movement-lab`. The Movement Gym remains directly openable on its own branch. The original production playground and progression fixture remain directly openable on this branch. The menu loads `Assets/WindrunnerFrontend/Scenes/StartingWorld.unity`, an integration copy of `Assets/AirflowPrototype/Generated/Batch1_Playground.unity`. The title and world have scene-scoped project roots. A short-lived handoff carries a validated slot store and progression service across a single scene transition. The input host and pause controller still own action maps, rebinding, cursor and time leases. The frontend applies navigation through those owners. A direct Editor launch of the integration world uses an in-memory progression store until the developer explicitly saves a copy.

`PlaythroughSlots` implements bound stores for the existing `ProgressionService`. The single authoritative slot payload contains schema version, stable world and checkpoint IDs, slot/display metadata, revision, UTC timestamp, and the existing progression state. Its quest/objective, relationship, reward, discovery, puzzle, challenge, cutscene and equipment-reference collections travel together. There is no authored dagger equipment system or transient ability serialization. The clearing anchor is currently the only supported restoration point. A valid save never instructs the loader to open an arbitrary scene or trust an arbitrary position.

Player slot directories live below `Application.persistentDataPath/Playthroughs-v1`; Editor playtests use `EditorPlaythroughs-v1`. Automated session tests use unique temporary directories. The slot writer flushes a temporary file on the same volume, publishes by replacement, maintains a recovery copy, checks SHA-256 and rejects stale revisions. Writers share an exclusive lock. A newer unsupported format is preserved. Confirmed deletion moves the entire slot to a hidden-from-the-list `deleted-<GUID>` directory. Import is offered only for the former `progression.json` at the known local-player path. It decodes into a new slot and preserves the source. Engineering fixture saves are excluded.

The integration copy uses an owned copy of the existing scene mixer. Music, Forest, Water and Environment faders expose the original gain stages. Preferences apply decibel offsets to their authored values. Music at 100% retains the original −15 dB snapshot, and ambience scales the three environmental buses together. The 25 direct sources still receive master gain. The standalone FEEL demo mixer is not the world's effects bus. No separate effects slider or subtitle toggle is shown; neither has an end-to-end production routing or subtitle implementation here.

## Developer validation

Use `Tools/Run-UnityTests.ps1 -Platform EditMode -Label <fresh-label>` and the corresponding PlayMode command. The rendered check uses `-Platform PlayMode -Rendered -Filter RenderedTitleAndScrollableSlots`. Run `python Tools/verify_serialized_contracts.py` and build with `Tools/Build-UnityCandidate.ps1 -MainMenu -Label <fresh-label>`. The Windows candidate packages just the title and the production integration world. `Tools/Smoke-UnityCandidate.ps1 -Label <same-label> -Rendered -Seconds 15` checks process initialization and bounded startup. All Unity commands require a closed Editor. `Documentation/TestResults.json` records the executable validation results.

## Integration audit

The production source scene matches progression baseline 9e8f97c4 byte-for-byte after normalizing checkout line endings. The integration copy retains the production character prefab and all referenced source scene IDs. Unity omitted one unreferenced stripped model GameObject proxy (867562219); its originating prefab instance 1472093721 remains in both scenes. Six new serialized objects are the arrival GameObject and Transform, player session, menu, progression host and actor. The loaded scene audit checks every component for missing scripts and every serialized nonzero object reference for resolution. The build-list audit permits exactly the two new scene entries and preserves all original flags and the Input System reference.

The production arrival anchor is (25.72, 121.29, -292.13), over walkable Terrain at y=119.95. The integration run verifies fresh Dash, Cast and Sling state after a reload and leaves a real reward Dash latched during an airborne autosave with movement input. Separate mouse and gamepad input events open Settings and Sound, back out and revert a display change. Isolated rebinding tests reject a conflict, save and reload an actual keyboard binding, restore defaults and retain stick sensitivity and inversion. The rendered test exercises 16 long playthrough names and scrolls controller focus to the last row at 1280×720, 1600×900 and 1920×1080.

In the production integration copy, 25 sources use direct output. The other 24 use the owned mixer: Music (1), Waterfall (1), Environment (11), Meadow Wind (1), Creek (4), Forest Wind (3) and Birds (3). The source mixer, source audio clips, source prefab configuration and production source scene are preserved. A repeat-load regression test caught additive attenuation; gain is now applied relative to the fixed authored snapshot every time. The owned mixer audit compares the original and copied signal chain, snapshot and routing after accounting for the mixer name and four exposed parameters.

## Windows candidate and remaining acceptance

Implementation checkpoints are 49cd4689 (persistence) and 272c450f (frontend integration). On Unity 6000.6.2f1 the final full suites passed 57/57 Edit Mode and 34/34 Play Mode, exit 0. The separate rendered test passed 1/1 at all three desktop resolutions. The serialized-contract audit returned zero failures. Earlier tests exposed a double-applied mixer offset, and an early automated mouse event omitted the button release. The corrected tests exercise both failure modes. The final Dash test maintains actual movement input; releasing movement naturally clears reward Dash in production.

Windows x64 candidate `windrunner-mainmenu-rc1` succeeded in 22.277 seconds with 0 errors, 24 warnings and a reported size of 1,212,310,368 bytes. It loaded the engine and survived a 15-second rendered player startup test with zero matched errors. Build warnings cover two mesh import/collision notices, three existing deprecated prototype API uses, two stripped Core debug shaders, three optional FEEL resource warnings and fourteen vendor shader diagnostics. See TestResults.json for the messages. The executable is `Builds/windrunner-mainmenu-rc1/Windrunner.exe`. The gameplay transition tests ran in Unity Play Mode. Physical controller ergonomics, audible balance, monitor-mode recovery on the target hardware and authored cinematic playback remain manual/content-dependent acceptance.
